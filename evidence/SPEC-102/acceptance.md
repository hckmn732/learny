# SPEC-102 — critères d'acceptation

Toutes les preuves ci-dessous proviennent de l'exécution réelle de `node tools/sdd/validate.mjs SPEC-102` (Supabase local, `LLM_MODE=mock`, horloge figée au 2026-11-11T12:20:00Z), sur la branche `spec/SPEC-102-schema-identite-et-preferences`.

- ✅ CA-1 — Après `createTestUser`, l'utilisateur possède exactement 1 profil, 1 `study_preferences`, 1 `notification_settings`, 10 `automation_settings` (valeurs EF-6, `enabled = true`), 0 `push_subscriptions` et 0 `pauses` : test d'intégration « creates exactly one profile, rhythm, notification and ten automations (CA-1) » dans `integration.json`.
- ✅ CA-2 — Les défauts de BR-ACC-08 (`2 h`, lundi→vendredi, soir), BR-NOT-04 (deux canaux, six types, `08:00`, `21:00 – 08:00`, week-end calme, plafond 5) et BR-ACC-12 (`fr`, `vous`, `Europe/Paris`, étape `profil`) sont comparés champ par champ : test d'intégration « applies the BR-ACC-08 and BR-NOT-04 defaults field by field (CA-2) » et cartes Profil, Rythme et Notifications du test e2e (`e2e.json`).
- ✅ CA-3 — CL-2 (fuseau invalide → `22023`, `invalid_timezone`), CL-3 (`study_days` `{}`, `{0}`, `{1,1}`, `{8}`, `hours_per_day` 0 et 7, `preferred_slots` vide → `23514`), CL-4 (`max_per_day = 4` → `23514`), CL-5 (deuxième pause active → `23505`), CL-6 (fin avant début, pause `ended` sans `ended_at` → `23514`) et CL-9 (e-mail refusé sous `authenticated` avec `42501` / `email_immutable`, accepté par le service) : test d'intégration « refuses invalid time zones, rhythm, cap, pauses and e-mail changes (CA-3, CL-2..CL-6) », test « refuses an e-mail change from an authenticated client, accepts it from the service (CL-9) » et carte « Contraintes » du test e2e (quatre SQLSTATE `22023`, `23514`, `23514`, `23505`).
- ✅ CA-4 — Les métadonnées d'inscription valides (`Alex`, `Perrin`, `America/New_York`, `en`) sont reprises, un prénom de 70 caractères est tronqué à 60, un fuseau `Mars/Olympus` et une langue `xx` retombent sur `Europe/Paris` et `fr`, l'absence de métadonnées donne les défauts : test d'intégration « copies valid sign-up metadata and falls back to defaults (CA-4, EF-2, CL-1) ».
- ✅ CA-5 — La suppression de la ligne `auth.users` supprime les lignes des six tables (profil, rythme, notifications, abonnement push, dix automatismes, pause) : test d'intégration « cascades the deletion of auth.users to the six tables (CA-5, EF-4) » ; le test e2e vérifie aussi que « Nettoyer » fait disparaître les cartes.
- ✅ CA-6 — `default_automation_params(k)` et `AUTOMATION_DEFAULTS[k]` sont identiques pour les dix clés : test d'intégration « keeps the SQL and TypeScript automation defaults identical (CA-6) » et test unitaire « mirrors the ten automation defaults with admitted values (EF-6, CA-6) » dans `unit.json` ; le test e2e compare également les `params` affichés aux constantes.
- ✅ CA-7 — La RLS est activée sur les six tables (`relrowsecurity`) et, sans politique, un client `authenticated` lit 0 ligne sur chacune : test d'intégration « enables RLS on the six tables and hides their rows from authenticated (CA-7) ». Le rejeu du déclencheur (CL-7, 10 automatismes sans doublon) et l'endpoint push dupliqué (CL-8, `23505`) sont couverts par « replays the sign-up logic without duplicating rows (CL-7) » et « refuses a duplicated push endpoint (CL-8) ».
- ✅ CA-8 — Le test e2e « initialisation du compte @SPEC-102 » ouvre `/_dev/sdd/SPEC-102`, crée l'utilisateur de démonstration, vérifie les cinq cartes dans l'ordre, les dix automatismes et les quatre refus, puis nettoie ; la vidéo est dans `video/` et la capture dans `screenshots/`. Le test visuel « page identité conforme @SPEC-102 @visual » vérifie les jetons, la structure et la ligne de base `apps/web/e2e/__screenshots__/p1/spec-102-identity.spec.ts/spec-102-demo-desktop-linux.png` (e-mail masqué), avec axe sans violation `serious`/`critical`.
